The Clean-Data Discipline

Half the job is wrangling; the other half is admitting you wrangled

notes by Vikrant ✏️

~ 13 min read ~

There is a famous statistic that 80% of a data scientist's time is spent on cleaning. The statistic is wrong because it understates.

Mental model: schema-first wrangling
Hold this picture. Before you write a single transform, write the **target schema**: the shape of the dataframe you need at the end. Columns, types, primary key, expected row count, what 'one row' represents.

Move 1 — The always-look-at-it rule

  • Aggregates lie. Rows tell the truth.
  • Step 1 — Define MAU numerically: 'A user who appeared in events.user_id at least once in a calendar month, where user is not in the test_accounts list, and event is not type=server_health'.
  • Step 2 — Eyeball 200 random rows: Print them. Spot the test accounts that did not get the team's @company.com filter, the duplicate user_ids from the SSO migration, the bot traffic from a load test on March 14.
  • Step 3 — Write the schema first: Target: one row per user_id per month. Columns: user_id (int), month (date), event_count (int). Primary key: (user_id, month). Expected ~125K rows for a month.
  • Step 4 — Transform with assertions: After each transform: assert row count in expected range, assert primary key uniqueness, assert no nulls in user_id. Three lines of pytest catch most pipeline bugs.
  • Step 5 — Cross-check against a known number: Compare your monthly active count for January 2026 against the company's already-published number. If yours differs by more than 2%, find the gap before publishing. The gap is almost always a definition difference.

Move 2 — The assumption ledger

  • Every cleaning decision you make adds an assumption. Drop rows where `country IS NULL`.

Traps to flag for the exam

The classic trap: skip EDA, jump to modeling: The most common failure mode in any data project: skip exploratory data analysis (EDA), feed the dirty data into a model, and report the model's accuracy as if it meant something. The model has no idea your `amount` column flipped from paise to rupees in April. It happily fits both regimes as one continuous variable and produces a confident, polished, completely wrong number.

Takeaways (memorize these)

Cleaning is not preamble to the work; cleaning is the work, and the model on top is decoration.
Schema-first wrangling: write the target shape before you write the first transform, validate after each transform.
Aggregates lie; rows tell the truth. Eyeball 200 random rows before publishing any number.
An assumption ledger turns every non-trivial cleaning decision from an opinion into a defensible record.
If two analysts produce different numbers from the same data, the difference is in their assumption ledgers — and the one without a ledger always loses the argument.
