Claude Code: Your Pair Engineer

Plan-then-execute teammate, not autocomplete

notes by Vikrant ✏️

~ 14 min read ~

Most engineers meet Claude Code expecting fancy autocomplete. They open the terminal, type *'add a login button'*, watch it run for forty minutes, and either get something brilliant or something that touched 14 files including the build config.

Mental model: Claude Code is a plan-then-execute teammate
Picture a junior engineer pair-programming with you. Before they touch a file they say *'so the plan is: change the User type, then update three call sites, then add a migration, then run the tests'*. You nod or push back. Then they execute, narrating as they go. If you skip the plan step you are not pair-programming; you are watching a junior wing it on the keyboard. Claude Code is exactly the same. **The plan is not a bureaucratic step; the plan is what makes the execution sane**.

Move 1: The Planner-Doer Split

  • Every non-trivial task should start with a planning subagent that reads code and writes a plan, **without modifying anything**. The built-in `Plan` subagent does exactly this.
  • /plan: Ask Claude Code to produce a plan: which routes, which DB tables, which env vars, which idempotency strategy, which retry behaviour, which test cases.
  • Review: Read the PLAN.md. Push back: 'we already have an events table, reuse it' or 'do not add a new env var'.
  • /implement: Run the doer. Sonnet 4.6 with the plan as context. Tell it to follow the plan strictly and stop if it deviates.
  • Inline review: Read every diff. The plan said 4 files; if 7 changed, ask why before approving.
  • Test: Tests run automatically in a pre-commit hook (configured in CLAUDE.md). Failed test = stop.
  • Commit: You commit, not Claude. The kernel hook blocks autonomous commits anyway.

Move 2: CLAUDE.md as Kernel

  • CLAUDE.md is a markdown file at the root of your repo that Claude Code reads at the start of every session. It is your **kernel** in the Linux sense: a small, durable, always-loaded set of rules that constrain everything else.

Traps to flag for the exam

The classic trap: the unbounded subagent: Subagents are powerful: `general-purpose` for multi-step research, `Plan` for read-only planning, `bug-hunter` for finding the root cause of a failure, `pr-reviewer` for reading a diff, `Explore` for codebase orientation. The trap: launching a subagent without a bounded brief and a hard stop. *'Investigate why the build is slow'* is unbounded; *'investigate why the build is slow, focus on the webpack config and the test pipeline, return a 5-bullet diagnosis'* is bounded. Unbounded subagents drift, cost more, and produce essays you have to read. Always give them a brief and a deliverable.

Takeaways (memorize these)

Claude Code without CLAUDE.md is expensive autocomplete; with a kernel it is a teammate.
Always /plan before /implement for anything 3+ files, auth, payments, or migrations.
The plan is reviewable in 2 minutes; the diff is reviewable in 2 hours. Cheaper to be wrong on the plan.
Subagents need bounded briefs and a deliverable; unbounded subagents drift.
Hooks enforce the rules you would otherwise have to enforce in code review.
