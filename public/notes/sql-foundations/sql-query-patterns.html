Subqueries, CTEs, and the Read-Order Lie

How execution order differs from write order, and why CTEs win

notes by Ishaan ✏️

~ 16 min read ~

Until now we've written queries small enough that 'what you write' and 'what runs' looked the same. This lesson is the moment they diverge — and the moment SQL becomes a language you can actually compose.

Mental model: what you write vs what runs
Write order: `SELECT … FROM … WHERE … GROUP BY … HAVING … ORDER BY … LIMIT`.

Move 1 — CTEs over scalar subqueries

  • There are three ways to compose queries: subqueries in WHERE/SELECT, derived tables in FROM, and CTEs (`WITH`). Subqueries in SELECT — *scalar subqueries* — are tempting and almost always a smell: ```sql -- ❌ Scalar subquery; runs once per row of the outer query SELECT name, (SELECT COUNT(*) FROM orders WHERE customer_id = c.id) AS order_count FROM customers c; ``` **CTE form** — same logic, single pass, easier to read, easier to optimize: ```sql -- ✅ CTE; database can plan and reuse WITH order_counts AS ( SELECT customer_id, COUNT(*) AS n FROM orders GROUP BY customer_id ) SELECT c.name, COALESCE(oc.n, 0) AS order_count FROM customers c LEFT JOIN order_counts oc ON oc.customer_id = c.id; ``` The rule: **scalar subqueries in SELECT are a code smell — refactor to a CTE + JOIN.** This is one of the few things in SQL where you can take a confident position.
  • 1. English: Top 5 cities by revenue in Q1 2026 (paid orders only), with each city's average order size.
  • 2. Stage 1 — Filter to relevant orders: Pre-filter; this is the WHERE. CTE makes it reusable.
  • 3. Stage 2 — Aggregate by city: Group, sum, average.
  • 4. Stage 3 — Top 5: Sort and slice.
  • 5. The shape: Pipeline reads top-to-bottom in the order of the question. No nesting. No re-reading. Reviewers love it; future-you loves it.

Move 2 — Compose CTEs into a pipeline

  • The real power of CTEs is composition. Each CTE is a named stage.

Traps to flag for the exam

The classic trap: 'I'll just nest one more subquery': Each subquery you nest is a private, anonymous chunk of logic that can't be reused, can't be inspected with a partial run, and can't be named in a code review. The fourth one is always the breaking point.

Takeaways (memorize these)

Execution order: FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY → LIMIT
Scalar subqueries in SELECT are a smell; refactor to a CTE + LEFT JOIN
CTEs are named stages — top-to-bottom pipeline, each name documents intent
If you nest a subquery more than two deep, you wanted a CTE
Plan in English first; translate to CTEs second; debug less
