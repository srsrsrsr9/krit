Why SQL Refuses to Die

Tables are spreadsheets with rules; queries are questions with grammar

SQL is the second-most-popular language in the world (after JavaScript) and has been for thirty years. Its grammar predates the iPhone.

Mental model: spreadsheets with rules
A SQL table is a spreadsheet that signed a contract.

Move 1 — SELECT, FROM, WHERE in plain English

  • Every SQL query is a sentence. Read it left to right and translate: ``` SELECT name, city ← these columns FROM customers ← from this table WHERE city = 'Mumbai' ← where this is true ``` In English: *give me the name and city of every customer in Mumbai*.
  • 1. English: Show me Bengaluru customers who signed up after April.
  • 2. The grain: We are asking about customers, one row per customer. So FROM customers.
  • 3. The columns: We want their identity and signup date. SELECT name, signed_up_at.
  • 4. The filter: Two conditions joined with AND: city is Bengaluru, and signed_up_at is after 2024-04-30.
  • 5. The full query: Read top to bottom; English question maps to SQL grammar.

Traps to flag for the exam

The classic trap: 'SELECT * for now': You're prototyping. You write `SELECT *` to see what's in the table. Then you copy that query into the production code. Then someone adds a column. Then you have a leak.

Takeaways (memorize these)

A SQL table is a spreadsheet with rules — fixed types, same shape per row, primary key indexes lookups
Every query is a sentence: SELECT <columns> FROM <table> WHERE <condition>
Always list columns; never `SELECT *` — it leaks data when schema drifts
WHERE filters rows; SELECT picks columns; ORDER BY sorts what survives
Single quotes for string literals — double quotes mean identifiers in standard SQL
