Filtering Without Crying

Operators, NULL semantics, and the WHERE-the-cat-sat-on trap

notes by Vikrant ✏️

~ 14 min read ~

Most SQL bugs that ship to production are filter bugs. Not the obvious kind.

Mental model: three-valued logic
Most languages have two truth values: true and false. **SQL has three: TRUE, FALSE, and UNKNOWN.** Whenever a condition involves a NULL, the result is UNKNOWN — not TRUE, not FALSE.

Move 1 — Operators that do what you mean

  • Operators in SQL look like the operators in your other language. They mostly behave the same.
  • 1. English: Orders from Pune or Bengaluru, with amount above 1000, placed in March or April 2026.
  • 2. The city filter: Two cities — use IN, not OR.
  • 3. The amount filter: Above 1000 means strictly greater.
  • 4. The date filter: March 1 to April 30, inclusive. BETWEEN handles this cleanly.
  • 5. Combine with AND: All three conditions must hold.

Move 2 — NULL is not a value

  • **NULL means *unknown* or *missing*.** It is not zero. It is not empty string.

Traps to flag for the exam

The classic trap: WHERE-the-cat-sat-on: Senior SQL writers call this *the WHERE-the-cat-sat-on bug*. The cat (NULL) was definitely on the mat, but your filter didn't see it because you assumed equality would touch every row.

Takeaways (memorize these)

SQL has three truth values: TRUE, FALSE, UNKNOWN — WHERE keeps only TRUE
NULL means 'unknown'; any operator applied to NULL returns NULL (UNKNOWN)
Use IS NULL / IS NOT NULL for NULL tests; never `= NULL`
Negative filters (`<>`, `NOT IN`) silently drop NULLs — handle them explicitly
COALESCE is the canonical fix when you want NULL to be treated as a known default
