GROUP BY Collapses Reality

Aggregation, HAVING vs WHERE, and the silent-NULL trap

notes by Karthik ✏️

~ 14 min read ~

Up to now we've been pulling rows. Most real questions don't want rows — they want *summaries*.

Mental model: GROUP BY is a controlled collapse
GROUP BY tells the database: *first sort all rows into buckets by this column, then collapse each bucket into one row using these aggregate functions.*

Move 1 — Pick the right aggregate

  • Five aggregates do 95 percent of the work: - **COUNT(\*)** — total rows in the group, including rows with NULLs - **COUNT(col)** — rows in the group where `col` IS NOT NULL - **SUM(col)** — sum of non-NULL values - **AVG(col)** — sum / count, ignoring NULLs (which is sometimes what you want, sometimes silently wrong) - **MIN/MAX(col)** — extremes; ignore NULL The trap: **COUNT(\*) and COUNT(col) are different.** If `discount` is sometimes NULL, `COUNT(discount)` undercounts vs `COUNT(*)` by exactly the number of NULLs.
  • 1. English: Top 3 cities by total orders, but only cities with at least 100 orders.
  • 2. The grain: We want one row per city. So GROUP BY city.
  • 3. The aggregate: Total orders per city — COUNT(*).
  • 4. The post-aggregate filter: 'At least 100 orders' is a condition on the aggregate, not the rows. That's HAVING, not WHERE.
  • 5. The full query: Sort by count, take 3.

Move 2 — HAVING vs WHERE — when each runs

  • WHERE filters **rows before** the GROUP BY. HAVING filters **groups after** the GROUP BY.

Takeaways (memorize these)

GROUP BY is a controlled collapse — buckets rows by a key, then aggregates each bucket
Every non-aggregated column in SELECT must appear in GROUP BY — anything else is ambiguous
COUNT(*) ≠ COUNT(col) when col contains NULLs
AVG silently ignores NULL — always show COUNT alongside AVG so readers can judge
WHERE filters rows before grouping; HAVING filters groups after — never confuse the two
