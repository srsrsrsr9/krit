The Test Pyramid and What to Test Where

Three altitudes, three different jobs, one bill at the end of the month

notes by Vikrant ✏️

~ 13 min read ~

Most teams have an *ice-cream cone* test suite, not a pyramid: 800 e2e tests on top, 14 integration tests in the middle, 6 unit tests at the bottom (left over from when they used Jest in 2019). The CI run takes 28 minutes, the flake rate is 14%, and nobody can tell you what would actually break if a specific function changed.

Mental model: tests live at three altitudes
Think of your suite as **three altitudes of flight**:

Move 1 — Unit-as-fast-feedback

  • The first job of unit tests is *not coverage*. It is **fast feedback while you are still holding the problem in your head**.
  • 1. The customer report: "When I check out with a UPI ID that has a dot, like sneha.s@okhdfc, the total shows ₹0."
  • 2. Where does the logic live?: The bug is in the `formatUpiId()` function. Pure input → output. No network, no DOM. This screams unit test.
  • 3. Write the unit test: Three lines. Runs in 4ms. No browser, no DB.
  • 4. Resist the urge to write an e2e: An e2e test for this would take 90 seconds, hit a real Razorpay sandbox, and prove the same thing as the 4ms unit test.
  • 5. Add ONE e2e for the critical path: Yes — *one* test that proves checkout end-to-end works for a UPI user. The unit test catches the formatting bug; the e2e catches the wiring.

Move 2 — E2E for the critical path

  • Now the top of the pyramid. **End-to-end tests are not for everything**.

Traps to flag for the exam

The classic trap: the inverted pyramid (the ice-cream cone): Teams build the cone for one of two reasons: either they hired a contractor who wrote 800 Selenium tests in 2019 and called it a day, or they confused *e2e* with *real testing* and treated unit tests as second-class citizens. Both end in the same place: 28-minute CI runs, 14% flake rates, and devs who learn to ignore the suite.

Takeaways (memorize these)

Tests live at three altitudes — unit, integration, e2e — each with a different cost-to-confidence ratio.
Unit-as-fast-feedback: if your unit test makes a network call, it isn't a unit test. It's a slow integration test in costume.
E2E for the critical path: the question is *who calls if this breaks?* If the answer is 'nobody', push the test down.
The ice-cream cone (lots of e2e, few unit) is the most common shape and the most expensive one. The fix is to rewrite, not delete.
Measure (duration × flake rate) before triaging. Deleting tests blind is how teams lose real coverage.
