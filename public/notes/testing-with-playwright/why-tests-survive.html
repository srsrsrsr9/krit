Why Tests Are Worth It (Even When They Slow You Down)

Tests are documentation for future-you, written in a language the runtime can verify

notes by Aanya ✏️

~ 13 min read ~

Every engineer has a test they wish they had written. It is usually the one they didn't, the night before the bug shipped, in the code path they were sure couldn't break.

Mental model: tests are documentation for future-you
Stop thinking of tests as a *safety net*. That metaphor makes them sound like insurance: boring, optional, paid for in case of disaster.

Move 1 — The regression bargain

  • Here is the bargain a test makes with you: *I will cost you 20 minutes today, and in exchange I will catch one specific bug forever, automatically, without you having to remember it exists.* That's it. That's the entire deal.
  • 1. Bug arrives in prod: On-call gets paged. Customer screenshot. Stack trace points to a `null` in checkout.
  • 2. Reproduce locally: Spend 15 min finding the input that triggers it. This is the expensive part. Don't waste it.
  • 3. Write the failing test FIRST: Before the fix. Same input. Watch it go red. This proves you actually understood the bug.
  • 4. Apply the fix: Now the fix is obvious because the test pinned down the exact behaviour you want.
  • 5. Watch the test go green: And it stays green forever. Future-you, refactoring this in 2027, gets a red CI before the bug ever ships again.

Move 2 — The coverage bait

  • Now the trap. Most teams who *do* invest in tests fall for **the coverage bait**: chasing a number — 80%, 90%, the magical 100% — instead of chasing the property the test should prove.

Traps to flag for the exam

The classic trap: confusing coverage with confidence: A 92% coverage badge on your README does not mean your product works. It means 92% of your lines were *executed* by some test, somewhere, at some point. Whether those tests asserted anything meaningful is a different question, and the badge will not tell you. Teams that optimise for coverage end up with brittle, low-value tests; teams that optimise for *catching the bugs that would actually ship* end up with fewer tests that pull more weight.

Takeaways (memorize these)

Tests are documentation for future-you, written in a language the runtime can verify.
The regression bargain: pay 5-20 minutes today for ~1,800 free CI passes per year. The math only looks bad if you assume the bug will never come back.
When fixing a bug, write the failing test *first*. The fix becomes obvious and the bug is locked out forever.
The coverage bait is the trap of optimising for a 92% number while shipping zero real signal. Coverage is necessary, not sufficient.
For every test, ask: *what specific bug would this catch?* If you can't answer in one sentence, it's theatre.
